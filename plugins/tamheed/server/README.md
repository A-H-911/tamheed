# Tamheed MCP server

Documents the tool surface as of **tamheed v6.4.0**. The bilingual user guide
(<https://github.com/A-H-911/tamheed/blob/main/index.html>) renders the same surface with every
parameter, read from this server at build time.

The **only write path** into a Tamheed package (ADR-0001). Agents interact with a package
exclusively through these MCP tools. Every write passes schema validation (FKs, CHECKs,
NOT NULL provenance), and queries return rows instead of whole documents. A constraint
violation surfaced by a tool *is* the quality-gate report. This server is the successor of
`validate_package.py`, the mechanical half of the capability the skill owns.

**The plugin also ships one hook (v5.1, plan 123).** `hooks/hooks.json` runs
`server/resume_hook.py` on every `SessionStart` (startup, resume, clear, compact, fork). It is a
stdlib script with no inline metadata (`uv run --no-project`, ~0.1 s). It finds the tamheed note in
the project's `CLAUDE.md` (or behind one `@` import). It loads the package locklessly
(`store.load`) and prints the **resume block**. The block is the same `_resume_block` `package_open`/`server_info`
return, as plain text, screened by the injection gate. It is capped at 40 lines (the entry itself
at 25 lines / 4,000 characters, the block's own cap, v5.2). On any failure it prints one line and
exits 0. It writes nothing and takes no lock. Its lock line carries what the store OBSERVED about
the holder (v5.3, plan 136). It reads
`holder observed not-running — package_unlock(confirm=true) on the operator's word` after a
process restart, and `alive` while a server holds the package. Opt-in trace
(v5.3): when `TAMHEED_HOOK_LOG` names a file that already exists, the hook appends one line of
counts per run, never the entry. The line is
`version=… source=… lines=… chars=… status=printed|silent|error:… session=<id>`. `version=` (since
v5.6, plan 151) is the hook's own release, so a line says which hook ran. So a field can tell "did
not fire" from "fired, not delivered". The `session=` tail (v5.4, plan 141) is the event's
`session_id`, the transcript's own file name. A line is attributed by it, never by its counts.
Every session that loaded the plugin in the folder prints the same block, a headless one another
tool starts included. A session started with no settings loaded, as an Agent SDK caller may
choose, loads no plugin and runs no hook (v5.5, measured). A plugin reload runs no `SessionStart`
hook (measured: 24 reloads, none). After one, `package_open` and `server_info` return the block.

## Install & launch

**Python floor: 3.10** (the `mcp` SDK's `requires-python = ">=3.10"`, verified 2026-07-17
from its pyproject). Program decision ASM-D raises the repo floor to match.

Plugin installs copy files only. They do not install Python packages. Two launch paths:

1. **`uv` (preferred, zero setup):** the server script carries PEP 723 inline metadata, so
   `uv run tamheed_server.py` fetches the SDK automatically. The bundled `.mcp.json` at the
   plugin root uses this path (`${CLAUDE_PLUGIN_ROOT}`-relative) and auto-starts the server
   when the plugin is enabled.
2. **pip fallback:** `pip install "mcp<2"`, then `python tamheed_server.py --package-dir <root>`.

If the SDK is missing the server exits with a one-line error naming both options, never a
silent dead server.

`--selftest` lists the tools. When the `mcp` SDK is importable, it registers every tool
with FastMCP and reports `N/N tools registered` (exit 1 on any registration failure).
Since v5.7 (plan 160) it also compares each description the SDK LISTS with the registry's
and with the client's cap. It exits 1 on a difference. **What a client receives as a
tool's description is the registered text, the second element of the `TOOLS` entry,
never the function's docstring.** Claude Code truncates a tool description at 2,048
characters. So a rule a caller must know stands in the registered text, short, with the
critical words first. Three tools carry such a contract: `entity_query`,
`progress_update` and `audit_record`.
`--package-dir <root>` sets the directory packages live under. Resolution is layered
(field-evidence C11, because a stdio server's cwd is not guaranteed). The order is explicit
flag > `CLAUDE_PROJECT_DIR` (exported by Claude Code to plugin server processes) > cwd. An
unexpanded `${...}` literal counts as unset. Every `package_*` result echoes the resolved
absolute root, and `server_info` reports it on demand.

## Rules

- **No raw SQL, ever.** Tools take structured, checked arguments. Unknown types/columns
  are rejected by name.
- **One external dependency, bounded (C33).** Everything is stdlib except the MCP SDK,
  pinned `mcp>=1.2,<2` in the PEP 723 header. SDK 2.0.0 removed `mcp.server.fastmcp`,
  and an unbounded resolve broke every fresh environment while cached ones kept working.
  `--selftest` reports SDK serving status (`mcp sdk: ok (<version>)`) without requiring
  it. The pin is never widened without a deliberate port to the SDK's successor module.
- **Single writer.** Opening a package takes `data/.lock` (from `db/store.py`). A second
  opener fails loud, and the lock names who holds it and since when. C31: a bare PID
  invited an unsound liveness check, because the OS reuses PIDs. The lock releases on
  `package_close` or process exit.
- **The working tree is the truth (C31).** Canonical `data/` lives in the project's git
  working tree. Uncommitted package writes are destroyed by `git reset --hard` /
  `checkout` / `stash` like any uncommitted change, so commit package data before branch
  operations. Writes refuse to overwrite a tree that moved underneath the open session
  (`StoreStaleError`: batch NOT applied, so close, reconcile via git, reopen). The
  append-only journal (`progress_entries`, `audit_verdicts`) rejects in-place rewrites.
  Corrections are appended, never edited.
- **Batch-first.** Mutation tools accept arrays and apply them in ONE transaction,
  all-or-nothing, with per-item verdicts naming any violated constraint.
- **Stored text is data, never instructions.** Brief-derived text is inert.
  `handoff_emit` runs a G-INJECT-style screen and refuses to emit instruction-shaped text.
  An `entity_export` file carries the same brief-derived text for a script to render. The
  script escapes it (the viewer's escape-first rule applies to consumers too).
- **Reads go through the tools too.** A committed script that must quote the store reads an
  `entity_export` file the tool wrote, never `data/*.jsonl`, never a pasted display. A
  full-row status flip names its untouched columns (`expect_unchanged`) and the store
  refuses transport drift.
- **Cascade-on-transition (C4).** State transitions (AC verdict → requirement auto-advance,
  edges → gate views) propagate via schema triggers/views in the same transaction. There is
  no "reconcile trackers" commit to forget.

## Tool reference

| Tool | Kind | Summary |
|---|---|---|
| `server_info(detail?)` | read | Server version (from the bundled `plugin.json`), resolved package root, open package, migrations head. It makes startup diagnosable (C11/C16). With a package open, `package` is its stored row: ALL ten header columns since plan 101 (the field's FB-015). They are name, title, profile, mode, iteration, `package_version`, `mvp_definition`, `entry_point`, `go_no_go`, `created_at`, a superset of what `entity_upsert(type="package")` writes. No other tool reads it, and a package resolves by DIRECTORY, so the stored name is descriptive. On a migrated package the block carries `v1_manifest_derived: ["mode", "profile", "created_at"]`, the same annotation `review.html` prints, as data (C18). `detail=true` adds `entity_types` (type, table, id prefix) and `relation_rules` (allowed endpoint types per relation): the vocabulary, without learning it from a refusal (plan 066). The header it reports is written with `entity_upsert(type="package")` (plan 094) |
| `package_create(name, title, profile, mode)` | mutate | Create under the package root. It seeds the `entity_types` registry and takes the lock. It wires the project (v6.2): the root `CLAUDE.md` pointer and the package's planning note, reported as `wiring` |
| `package_open(name)` | mutate | Open an existing package (takes the lock). A refusal on a held lock reports what the store OBSERVED about the holder, with the evidence (plan 063). The observation is `not-running`, `reused`, `alive` or `unobservable`. A root `CLAUDE.md` without a Tamheed section is wired on open, once (v6.2, `wiring`). Since v6.3 (plan 217) the result warns on `.unflushed` sidecars left by an earlier close. A stale `.writing` temp is removed. |
| `package_unlock(name, confirm?)` | read by default. `confirm=true` removes `data/.lock` + 1 journal row | The sanctioned route out of a lock whose holder is gone (findings_25 §1, plan 064). Default = REPORT: the lock, the observation and whether confirm would proceed, nothing written. `confirm=true` is OPERATOR-WORDS-ONLY, like `force`. It proceeds only when the holder was observed `not-running` or `reused`. Reused means pid recycled, decided by the process start identity the lock records, never by a bare liveness check. It REFUSES on `alive` and on `unobservable` (another host or pid namespace, access denied, a legacy lock, a platform that cannot report a start time). Removing `data/.lock` by hand stays the deliberate path for what this host cannot see. It first proves the on-disk store loads and removes only the exact lock bytes it judged. Then it opens, appends one `forced-override` row (actor `system:package-unlock`), and closes |
| `package_close()` | mutate | Write back canonical JSONL, release the lock. Every write already flushed canonical JSONL through the store, so close releases the lock. It is not the moment data reaches disk. Since v6.3 (plan 217) a final flush that stops on a file keeps that table's bytes as `data/<table>.jsonl.unflushed`. The result names them (`flushed: false`, `unflushed`). |
| `entity_upsert(entities[])` | mutate | Batch upsert. Items are `{"type": ..., <columns>}`, with per-item verdicts, all-or-nothing. The **lesson confirm guard** (plan 036) covers a write landing a lesson in `Approved`/`Promoted` from any other state. A new row born there is included. It is refused without `"operator_confirm": true` (operator-words-only, the `force` doctrine). Content must be byte-identical to the stored row. Approval requires non-empty `confirmed_by` on that write. Promotion requires stored-`Approved` + `promoted_to` naming an existing `SKL-` row. The server appends a `correction` journal row naming it (actor `system:edge-retire`) in the same transaction. An absent triple is an error (an attempt is not a write). Retype in ONE batch: the retire item + the corrected edge. An UPDATE's per-item result carries `changed_columns`, each `{column, old_len, new_len}` for text (plan 080). So a re-sent long field that lost a paragraph shows as a length drop. JSON columns compare as parsed values, as `expect_unchanged` does. LESSONS (plan 075): approving or promoting a lesson retires every binding lesson whose `superseded_by` names it, in the same write. There is one `transition` journal row each, and the ids are returned as `superseded`. On an Approved/Promoted lesson ANY move off a binding status, and any change to `superseded_by`, is refused without `operator_confirm`. What binds on the operator's word is retired on it too. A by-hand lesson retirement is an Approved/Promoted row moved off a binding status on the operator's word. The engine journals it as a `transition` row by `system:lesson-guard`, returned as `lesson_audit` (plan 086). The automatic path keeps `system:lesson-supersession`. FEEDBACK (plan 087): an `FB-` row is born Proposed freely. `Confirmed` needs `operator_confirm` + `confirmed_by` and is journaled (`system:feedback-guard`, returned as `feedback_audit`). A `local-tool` kind arriving on any row needs the word and lands it Confirmed. While Confirmed/Reported/Resolved the row's content changes only with the word, and leaving that set is journaled too. The content is `kind`, `title`, `detail`, `workaround`, `tool_path`, `tool_or_rule`, `confirmed_by`. THE HEADER (plan 094): an item `{"type": "package", ...}` writes the one header row of the open package. The columns are `title`, `mode`, `iteration` (an integer), `mvp_definition`, `entry_point`, `go_no_go`. Identity columns (`name`, `profile`, `package_version`, `created_at`) are refused by name. `go_no_go` is the governance verdict and changes only with `operator_confirm`, journaled as `system:package-guard` and returned as `package_audit`. The header is never a family (no register, no CSV, no registry row). THE SUBSTITUTE (plan 095): `{"type", "id", "substitute": {"<column>": ["<old>", "<new>"]}}` (only `operator_confirm`/`expect_unchanged` beside it) changes one token in one column without the whole row passing through your output. The server materializes the stored row, replaces the exact text, and sends the result down the ordinary full-row path. So every guard, trigger, `expect_unchanged` and `changed_columns` judge it as a caller's row, and the item reports `substituted` counts. Refused by name: a mixed item, the journal, composite-key rows, `id`, a non-TEXT column, zero occurrences, and `custom_attributes` that would stop parsing. Also refused: a match glued to a digit (`DEC-20` inside `DEC-208` is never rewritten), and (plan 102) the RE-RUN shape. The RE-RUN shape is `new` contains `old` and already occurs. `scripts/X` → `src/web/scripts/X` run twice would double the prefix, so bound the needle with its delimiters. THE OPERATOR'S WORD is the JSON boolean `true` and nothing else on every guard (plan 094's security review). Since plan 102 `go_no_go` is PRESENCE-checked: name it only when changing it, on the word, and a header copied from `server_info().package` is refused unattended. `expect_unchanged` honours omission: a SENT column must match, and an OMITTED column is preserved by the UPDATE and never counts as drift. Beside a `substitute` the whole materialized row is checked. THE FEEDBACK DISPOSITION RECIPE (plan 100): a partial row of `id`, `kind`, `title`, `lifecycle_status`, `resolved_in`, `upstream_ref`. Omitted columns are preserved, and their absence from `changed_columns` is the proof. The engine journals the move. It needs no `expect_unchanged` (plan 108: naming a column the item does not carry is refused, because the assertion would be vacuous). "Omitted columns are preserved" is narrower than it reads (plan 112, the field's finding). A partial row must still carry every NOT NULL column of its table. A bare `{id, pinned}` on a lesson is refused on `title`. The recipe's six columns are the feedback table's NOT NULL set plus the three that move. THE CHEAPEST STATUS FLIP (the field's finding, 25 moves in one round): `substitute` on `lifecycle_status`, `{"substitute": {"lifecycle_status": ["Open", "Fixed"]}}`. It moves a status with zero transport of any long column and passes every guard the full row would. Since v6.3 (plan 217) a flush that stops on one file returns `ok: false`, `applied: true` and a `flush` report beside the items. The next write flushes the rest. |
| `entity_query(type, id?, status?, columns?, limit?, after_id?, ids?, search?)` | read | Targeted rows from one family, token-lean. Since v5.2 (plan 131) every SUCCESSFUL result carries `skill: "tamheed:reading-the-record"`, an empty `count: 0` included. A usage error (unknown type or column, an argument conflict) carries none. The row arrives with its cue, and the `entity_export` file never carries it. It returns `total` beside the LIMIT'd rows so truncation is never silent. Rows come in id order: prefix, then the id's first number, then the id, the review page's rule (v5.7, plan 160, text order before it). `limit` cuts from the lowest, so a limited read returns the first ids, never the newest rows (the `resume` block carries the newest journal entries). And (v4.5, findings_22 §1) the means to reach past it. `after_id` is keyset paging. The cut is the order's own comparison, so a walk is complete. It returns the rows AFTER an id, which the caller may type and which need not name a row. Only an id's first number counts, and what follows it orders as text. The result's `next_after` is the cursor, exact via a one-row look-ahead, null on the last page. `total` counts the filtered set, constant across a walk. `ids` reads a known set in one call, in id order, with absent ids simply missing. `search` is a case-insensitive substring over the family's TEXT columns, `%`/`_` escaped. `limit` cuts ROWS, never fields. There is no field truncation in the query path, and a payload cap is the client's. Reads announce what they hid (plan 068). With `columns` the result carries `omitted_columns`. With `search` it carries `matched`, `{id: [columns]}`. `search` is a substring match (case-insensitive for ASCII, SQLite's default `LIKE`) over EVERY text column including `custom_attributes`. A hit in an unprojected column otherwise reads as a fuzzy match. Both are siblings of `rows`, and row dicts never change. With `context=N` the result carries `occurrences: {id: {column: {count, snippets}}}`, a census. The counts are exact on the raw needle with `LIKE`'s ASCII case folding. ## HTML review surface (plan 012)

`export_html()` renders the open package's **only human review surface** (D-REVIEW: HTML,
never derived Markdown) to `<package>/review.html`. The page has twelve sections, and the
`generate-report` skill names them. They start with the overview with per-gate chips, the
resume block, and the traceability flow and matrix. They continue through the registers (with
`last_referenced` and the three-axis status columns) and execution progress (AC × audit verdicts,
progress log, scope changes). They end with readiness, lessons, feedback and the gap/screening
notes. The file is self-contained
static HTML (embedded CSS, restrictive CSP, zero JavaScript, zero data-derived links, every data
string escaped at render time). It is deterministic (same DB state and same UTC date ⇒
byte-identical output), so **commit it to the package's repo**. Its diffs are meaningful and
reviewers open it without running anything. Every section carries a freshness stamp derived from
the package's own stored timestamps, never the wall clock. The page's one clock is the date its
Readiness section was evaluated on. An export on a later date moves that date, and a rule that
reads the calendar may move its row. `review_current` compares the store's digest and is
unaffected by the date.

## Contract

The tool surface is a public contract. Additive changes are MINOR, breaking changes are
MAJOR + migration note (governance versioning applies to tools). Handlers are plain
functions, and `tests/test_mcp_contract.py` drives them in-process with no transport.

## scratch_diff — field-level package comparison

`python <plugin>/scripts/scratch_diff.py <a>/data <b>/data` (add `--json` for machine
output) diffs two packages row-by-row with correct per-table keying (`trace_edges` on
from/to/relation, `entity_types` on `type_id`, …). It uses the union of columns INCLUDING
JSON blobs (`custom_attributes`), because a diff that skips blobs silently under-reports
(field-evidence C28). Exit 1 (differences) is a report, not a failure. Bucket every
difference as expected or UNEXPECTED. An empty UNEXPECTED bucket is the pass
criterion. Standard uses: comparing a package against its `data-v3-backup/`, or a
re-recorded scratch package against the live one. Remove the scratch afterwards, because it
is a measurement, never a candidate.
